# Stuckpoint

> 사용자가 막히는 순간을 스크립트 한 줄로 잡아내는 3KB(gzip) 브라우저 SDK와 대시보드

분석 도구는 "몇 명이 이탈했는지"는 알려주지만 "어디서 막혔는지"는 잘 알려주지 않습니다.
Stuckpoint는 사용자의 답답함이 **행동으로 드러나는 네 가지 순간**을 감지해, 문제가 된 버튼과 입력칸을 정확히 짚어줍니다.

- **데모**: 일부러 불편하게 만든 결제 화면 → `/demo` (고친 버전 `/demo/fixed`)
- **대시보드**: 데모에서 막힌 기록이 3초마다 갱신 → `/dashboard`

## 왜 만들었나

QA 테스터로 일하며 배운 것은 "사용자는 화면이 아니라 막히는 순간을 기억한다"는 것이었습니다.
그런데 그 순간은 대부분 조용히 지나갑니다. 사용자는 버그 리포트를 쓰지 않고, 버튼을 몇 번 더 누르다가 떠납니다.
그 "몇 번 더 누르는" 행동을 신호로 바꾸면, 누가 말해주지 않아도 고칠 곳을 찾을 수 있다고 생각했습니다.

## 감지하는 것

| 종류 | 판정 기준 | 이런 상황 |
| --- | --- | --- |
| **분노 클릭** | 반경 32px 안을 800ms 간격 이내로 3번 이상 누름. 연타가 끝나면 최종 횟수로 1건 | 결제 버튼이 아무 표시 없이 3초를 기다리게 함 |
| **반응 없는 클릭** | 눌릴 것처럼 생긴 요소(버튼 · 링크 · 손가락 커서)를 눌렀는데 1초 동안 DOM 변화 · 주소 변경 · 포커스 이동이 없음 | 손가락 커서가 뜨는 상품 사진을 눌러도 아무것도 안 열림 |
| **폼 이탈** | 한 칸 이상 입력하고 제출하지 않은 채 떠나거나 폼이 사라짐. 제출 후 다시 고치다 떠나면 이탈로 셈 | 연락처에 하이픈을 넣으면 이유 없이 결제가 안 됨 |
| **클릭 후 오류** | 누르고 1초 안에 잡히지 않은 오류(`error` · `unhandledrejection`) | 응답 모양이 바뀌어 `undefined.balance`를 읽다 오류 |

여기에 경로별 **방문**을 함께 보내서, "막힘 0건"이 방문이 없어서인지 정말 막힘이 없어서인지 구분하고 **막힘을 겪은 방문 비율**을 계산합니다.

## 설치

```html
<script src="https://<배포 주소>/stuckpoint.global.js" data-key="my-site" defer></script>
```

```ts
import { init } from "stuckpoint";

const sp = init({ endpoint: "https://<배포 주소>/api/collect", projectKey: "my-site" });
// SPA에서 정리할 때: sp.destroy()  (남은 기록을 보내고 리스너를 뗀다)
```

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `sampleRate` | `1` | 방문의 몇 %만 기록할지 (방문 단위로 결정) |
| `rageClicks` / `rageWindow` | `3` / `800` | 분노 클릭 기준 |
| `deadDelay` | `1000` | 반응을 기다리는 시간(ms) |
| `ignore` | – | 이 선택자 안의 요소 · 변화는 무시 |
| `trackClicks` | `false` | 링크 · 버튼 클릭도 기록 (script 태그는 `data-clicks="true"`). 링크는 이동 주소를 쿼리 없이 남김 |
| `onEvent` | – | 감지될 때마다 호출. `false`를 돌려주면 보내지 않음 |

- 이름표: `data-stuckpoint-label="한평생 오피스 · 프로젝트 보기"`처럼 붙이면 같은 글자의 버튼도 구분됩니다.
- 내 방문 빼기: 주소에 `?stuckpoint=off`를 붙여 한 번 열면 그 브라우저는 계속 빠집니다 (`?stuckpoint=on`으로 되돌림). 자동화 브라우저(`navigator.webdriver`)는 기록하지 않습니다.
- 대시보드: `PUBLIC_KEYS`(기본 `demo`)만 공개이고, 나머지 프로젝트는 `/dashboard?key=<키>&token=<DASHBOARD_TOKEN>`으로만 볼 수 있습니다.

## 설계하면서 고민한 것

**오탐을 줄이는 게 핵심이었습니다.** 처음 만든 반응 없는 클릭 감지기는 실제 사용에서 대부분 틀렸습니다. 고친 과정이 이 프로젝트의 대부분입니다.

- **포커스 비교 시점** — 처음엔 1초 뒤에 포커스가 바뀌었는지 봤는데, 사용자가 포기하고 다음 칸을 누르면 그게 "반응"으로 잡혔습니다. 클릭 직후 100ms 안의 포커스 이동만 반응으로 봅니다.
- **상관없는 화면 변화** — 시계 · 슬라이드 · 알림처럼 클릭과 무관하게 바뀌는 곳이 있으면 모든 클릭이 정상으로 판정됐습니다. `data-stuckpoint-ignore` 영역과 입력창 자체의 속성 변화(타이핑 · 자동완성)는 반응에서 뺐습니다.
- **cursor 상속** — 손가락 커서는 자식에게 상속돼서 아이콘 `<span>`이 잡혔습니다. 손가락 커서가 시작되는 가장 바깥 요소를 고릅니다.
- **연타 중복** — 같은 버튼을 5번 누르면 반응 없는 클릭 5건 + 분노 클릭 1건이 됐습니다. 판정 중인 요소는 다시 세지 않습니다.

그 밖에

- **선택자에 해시 클래스를 쓰지 않음** — CSS Modules · Tailwind 해시는 배포마다 바뀝니다. `data-testid` → 안정적인 id → `태그:nth-of-type` 순으로 만들고, `:r12:` 같은 자동 생성 id는 건너뜁니다.
- **히트맵을 좌표가 아니라 요소 기준으로** — 방문자마다 화면 폭이 달라 좌표는 흩어집니다. 대시보드는 페이지를 iframe으로 띄우고 기록된 선택자로 요소를 다시 찾아 그 위에 표시합니다.
- **행동한 시점의 페이지를 기록** — SPA에서 폼을 쓰다 다른 화면으로 가면, 감지가 끝나는 시점엔 주소가 이미 바뀌어 있습니다. 상호작용할 때 경로를 저장해 둡니다.
- **전송** — 10건 또는 5초마다 묶어서 `fetch(keepalive)`, 탭을 닫을 땐 `sendBeacon`. 본문을 `text/plain`으로 보내 다른 도메인에서도 CORS 사전 요청이 생기지 않습니다.
- **개인정보** — 입력값은 읽지 않고 입력창은 `name`으로만 남깁니다. 쿠키 없이 sessionStorage의 무작위 id만 씁니다. `data-stuckpoint-mask` 영역은 글자 대신 태그 이름만 남깁니다.

## 구조

```
packages/sdk        브라우저 SDK (TypeScript, 의존성 0) · tsup으로 ESM/CJS/IIFE 빌드 · Vitest + jsdom 테스트
apps/web            Next.js 15 (App Router)
  /demo             일부러 불편하게 만든 결제 화면 + 고친 버전
  /dashboard        막힌 곳 순위 · 화면 위 표시 · 폼 이탈 지점 · 전후 비교 · 실시간 기록
  /api/collect      공개 수집 주소 (형식 검증 · 길이 제한 · IP별 속도 제한 · 허용된 키만)
  /api/stats        집계
  src/lib/store.ts  저장소 교체 가능: Supabase(배포) / 로컬 JSON 파일(개발)
```

## 실행

```bash
npm install
npm test            # SDK 테스트
npm run dev         # SDK 빌드 후 http://localhost:3100
```

배포할 때는 Supabase에서 `apps/web/supabase/schema.sql`을 실행하고 `apps/web/.env.example`의 값을 채웁니다.
값이 없으면 `apps/web/.data/events.json`에 저장합니다.
